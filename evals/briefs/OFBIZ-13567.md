# OFBIZ-13567 — Add real POI-based .xlsx export via a new screenxlsx view-handler type

**Tipo:** New Feature · **Prioridad:** Major · **Componentes:** framework/widget

## Descripción

h3. Problem

The {{screenxls}} view-handler type ({{MacroScreenViewHandler}}, driven by {{XlsFormMacroLibrary.ftl}}/{{XlsScreenMacroLibrary.ftl}} under {{themes/common-theme}}) claims a content-type of {{application/vnd.ms-excel}} but never produces a real binary workbook - the macros only emit plain HTML {{<table>}} markup. Excel opens this leniently (with a "file format doesn't match extension" warning), but other tools (LibreOffice, Google Sheets import, etc.) are far less forgiving. Apache POI ({{org.apache.poi:poi}}) is already a framework dependency, but only used for spreadsheet *import* today ({{ImportProductServices.java}}) - there's no export usage to build on.

h3. Proposal

Add a new {{screenxlsx}} view-handler type (content-type {{application/vnd.openxmlformats-officedocument.spreadsheetml.sheet}}) that produces a genuine binary {{.xlsx}} workbook via Apache POI. Since a real {{.xlsx}} is a binary format, this needs a different rendering approach than the FreeMarker-macro pipeline {{screenxls}}/{{screencsv}}/{{screen}} share - likely a new {{AbstractViewHandler}} implementation (see {{ScreenFopViewHandler}} for how PDF output handles a non-macro rendering path) paired with a {{FormStringRenderer}} implementation that writes POI cells directly instead of macro-call text.

h3. Acceptance Criteria

* New {{screenxlsx}} view-handler type registered in {{handlers-controller.xml}}
* Produces a real, valid OOXML {{.xlsx}} binary - opens cleanly in Excel and LibreOffice with no format-mismatch warning
* Supports typed cells where the underlying field type allows it (numeric for currency/accounting-number fields, real dates for date/date-time fields), not just text
* Proven end-to-end via at least one demo screen (the existing {{WebtoolsLayoutDemoXls}}/{{ListExampleExport}}/{{ExampleReportXls}} example screens are the only current {{screenxls}} consumers)

h3. Note

Once this lands, {{screenxls}} becomes obsolete: everything it's used for, {{screenxlsx}} now does correctly with a genuine binary workbook instead of an HTML table masquerading as one. Removing {{screenxls}} is a separate, later candidate - it's a public view-handler type that unknown downstream {{controller.xml}} files may still declare, so retiring it needs its own deprecation cycle rather than piggybacking on this ticket.

## Criterios de aceptación

- **AC-1** New {{screenxlsx}} view-handler type registered in {{handlers-controller.xml}}
- **AC-2** Produces a real, valid OOXML {{.xlsx}} binary - opens cleanly in Excel and LibreOffice with no format-mismatch warning
- **AC-3** Supports typed cells where the underlying field type allows it (numeric for currency/accounting-number fields, real dates for date/date-time fields), not just text
- **AC-4** Proven end-to-end via at least one demo screen (the existing {{WebtoolsLayoutDemoXls}}/{{ListExampleExport}}/{{ExampleReportXls}} example screens are the only current {{screenxls}} consumers)

## Comentarios

### Comentario 1

h3. Load & Memory Benchmark Results (screenxlsx vs screenxls, matched dataset)

A benchmark was run to directly compare screenxlsx against screenxls on the *same* synthetic dataset and screen, differing only in view-handler type, with continuous heap sampling (jstat, forced GC before each run) rather than a single before/after snapshot.

h4. Methodology note

Non-paginated grids/forms are capped at 10,000 rows by ModelForm.MAX_PAGE_SIZE regardless of requested row count (Paginator.java). This test used paginate="true" with an explicit large view-size to genuinely render the requested row counts at each tier, confirmed by checking the exact row count in every output file. This cap applies identically to screenxls, so it isn't specific to the new code.

h4. Sequential, single request

|| Rows || screenxlsx time || screenxlsx heap delta || screenxls time || screenxls heap delta ||
| 10,000 | 0.42s | 124 MB | 1.67s | 300 MB |
| 50,000 | 1.15s | 301 MB | 8.40s | 307 MB |
| 100,000 | 2.17s | 307 MB | 16.90s | 355 MB |
| 250,000 | 5.29s | 338 MB | 41.76s | 508 MB |
| 500,000 | 10.37s | 749 MB | 92.06s | 785 MB (peak 939 MB, ~8% from the 1 GB heap cap) |

All outputs verified as complete (exact row counts checked, zip integrity confirmed for .xlsx) - none were truncated.

h4. Concurrent, 5 simultaneous users x 50,000 rows each

|| || screenxlsx || screenxls ||
| Total wall time | 1.88s | 21.33s |
| Peak heap delta | 555 MB | 803 MB (peak 940 MB) |

h4. Conclusion

screenxlsx is consistently 4-11x faster than screenxls at every tier tested, and uses less peak heap at every tier, including 500k sequential rows and 250k rows across 5 concurrent users. screenxls came within roughly 8-9% of a 1 GB heap ceiling at the largest tiers tested; screenxlsx retained comfortable headroom throughout. Both mechanisms' heap usage grows with row count, since the input data list itself (shared identically by both view-handlers in this test) is genuinely resident in memory - but screenxlsx's growth stays visibly flatter, and its time-to-completion advantage holds at every scale. This is consistent with SXSSFWorkbook's bounded-row-window design versus the per-cell FreeMarker-macro overhead of the screenxls path.

This confirms screenxlsx handles the volumes screenxls was designed for, at least as well and generally much faster, with no sign of the historical Apache POI OOM issues described in this thread.

Commit bd4bff1b8749151b473b361d0814cfaca610b99b in ofbiz-framework's branch refs/heads/trunk from Mridul Pathak

Implemented: real POI-based .xlsx export via a new screenxlsx view-handler type (OFBIZ-13567)

Adds a new screenxlsx view-handler type that renders screens as genuine binary .xlsx workbooks through Apache POI, additive alongside the existing screenxls/screencsv types.

- ScreenXlsxViewHandler drives the existing, unmodified ScreenRenderer/FormRenderer widget-tree walk through two new renderer implementations
- XlsxFormRenderer writes typed POI cells for form/grid data: NUMERIC for currency/accounting-number fields, real Excel dates for date/date-time fields, STRING otherwise, always falling back to STRING on any unparseable value
- XlsxScreenStringRenderer is a no-op renderer that lets the screen tree walk complete, since only form/grid content is in scope
- New poi-ooxml Gradle dependency supplies the XSSF/SXSSF classes core POI lacks
- New WebtoolsLayoutDemoXlsx demo view-map proves the mechanism end-to-end alongside its existing screenxls counterpart, producing a real, correctly-typed multi-sheet workbook
- New CommonViewAsXlsx UI label for the matching entry points added on the plugins/example side
- Includes unit test coverage for the renderer's row/column/cell-typing logic
